# System check

How to find out whether every backend actually implements the framework,
instead of finding out from a user on one platform.

## Capability coverage (static)

```text
cargo test -p capability-coverage     # the gate
cargo run  -p capability-coverage     # the matrix, as Markdown
```

Most methods on the `caps::*Ops` traits have a default body, and many of
those defaults do nothing: `StyleOps::attach_states` lights no hover or
press style, `TextInputOps::update_text_input_value` drops every value
written from code, `AppEnvOps::url_opener` makes `open_url` a no-op. A
backend that never overrides one compiles and runs without the feature,
and none of its own tests mention the method.

The check reads every backend's source (with `syn`, so one host checks all
of them, whatever they compile for) and flags a method on a backend when:

- the trait gives the method a default body,
- the backend does not override it, and
- another checked backend does.

Every flag has to appear in `crates/dev/capability-coverage/coverage.toml`
as either `na` (the default is right there, with the reason: no hover on a
touch screen, no soft keyboard on a desktop, a DOM-only hook) or `gap`
(missing, to be implemented). The test fails on a flag the file doesn't
list, and on an entry that no longer flags. So implementing a gap means
deleting its line, and a new silent no-op can't land unnoticed.

In the matrix, `✓` = implemented, `—` = not applicable, `✗` = known gap,
`?` = unlisted.

What it can't see:

- **A body that compiles but does nothing useful.** An override that
  returns a placeholder (Windows' `create_virtualizer`) counts as
  implemented. The runtime checks cover those.
- **Impls generated by macros.** No backend does this for capability
  traits; one that started to would show up as flags.
- **terminal and cpu** have one wildcard `gap` entry each, because nobody
  has reviewed them method by method yet. A new gap on either one won't
  fail the check until someone does.

## The system check screen (runtime)

The conformance app (`crates/dev/robot-e2e/examples/conformance`) has a
**System check** screen with a section for each capability whose default
silently does nothing:
- hover, press and cursor
- text input: values from code, focus, placeholder, Enter
- text area
- virtualized list
- scroll-end
- external links
- presence animation
- keyboard focus

Each section holds a fixture (`system_check.rs`) and checks it two ways.

**Automated.** The `capabilities` suite (`suites.rs`) drives the fixtures
through the robot when the app starts, as part of the normal run. Each
section shows its verdict as the run reaches it, and the run ends with the
usual `[E2E-RESULT]` line, which now counts `skip` separately:

```text
idealyst dev --macos --local crates/dev/robot-e2e/examples/conformance
# … [E2E-RESULT] {"suites":7,"tests":20,"pass":20,"fail":0,"skip":0,…}
```

The checks use real platform input and read back the native widget, so a
backend that only pretends fails them:

- `hover()` / `press()` / `release()` go through `hover_native` /
  `press_native` / `release_native`, and `to_be_hovered()` /
  `to_be_pressed()` read the style's own state (`get_state`'s `hovered` /
  `pressed`).
- `to_show_native_text()` reads what the widget displays
  (`introspect_native`). The robot's own `value` follows the bound signal
  even when the widget didn't.

A check **skips** instead of failing where the platform has no such thing:
touch platforms can't hover, and the robot can't read CSS `:hover` on web.
A skip shows its reason. It is not a pass.

**Manual.** What a robot can't judge is a checklist row under the same
fixture:
- the cursor shape
- whether an animation animates
- Enter in a field
- Tab between controls
- the placeholder text
- the scrollbar

Each row has instructions and Pass / Fail / Skip buttons. **Report** logs
every verdict, automated and manual, as one line:

```text
[CHECK-RESULT] {"platform":"MacOs","automated":[…],"manual":{"hover":"pass",…}}
```

Run it on each platform and compare the lines.

**Adding a capability.** Add a fixture plus a `Manual` entry in
`system_check.rs`, and a test in `capabilities_suite` whose name matches
the entry's `tests` list. If the automated check needs a new robot ability,
the robot grows it on every backend that can do it. Robot docs:
[`robot.md`](./robot.md).
