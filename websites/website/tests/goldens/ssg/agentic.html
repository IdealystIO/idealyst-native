Robot & MCP
Robot & MCPFirst-class automation and agentic control: one introspection registry drives E2E test harnesses, IDE tooling, and an MCP server an LLM can use as a tool surface.
The introspection registryEvery mounted primitive registers itself with a shared registry. Each entry carries a stable handle, a `test_id`, a label, and a primitive kind. The registry is platform-agnostic — the same shape is populated on web, iOS, Android, and any backend you add.Three consumers read from the same registry — the test harness, the IDE inspector, and the MCP server. They don't know about each other, but they read identical data.
The Robot bridgeQuery elements by label / kind / `test_id`, click, type, set toggles, scroll, read signals, take real-surface screenshots, and snapshot the tree — over one wire protocol that every backend serves. A test suite written once drives the app on web, iOS, Android, and macOS.
# The bridge is newline-delimited JSON over TCP. Every consumer —
# tests, the inspector, MCP — speaks the same verbs:
{"id":1,"cmd":"find_element","args":{"label_contains":"Dark mode"}}
{"id":2,"cmd":"click","args":{"element_id":154}}
{"id":3,"cmd":"screenshot","args":{}}

# Run a Rust test suite over that bridge, on any platform:
idealyst test --macos
`idealyst test` wraps the bridge in a Rust harness: `#[robot_test]` fns expand to ordinary `#[test]`s that launch (or attach to) the app, locate elements, act, and assert on signals and labels — pass/fail lands in your normal test output.
`#[method]` fnsInside a `#[component]` body, nested fns marked `#[method]` become the component's imperative handle, registered as JSON-callable. Methods are commands (they return `()`); reads stay signals. External automation invokes them by name with no per-app glue.
#[component]
pub fn Cart() -> Element {
    let items = signal(Vec::<Item>::new());
    
    #[method]
    fn add(item: Item) {
        items.update(|v| v.push(item));
    }
    
    #[method]
    fn clear() {
        items.set(Vec::new());
    }
    
    // ...the rest of the component
}
The component's `cart.add(...)` and `cart.clear()` are now callable from a Robot test, an IDE inspector, or an LLM tool call — same surface, three consumers.
MCP server`idealyst mcp` serves the framework catalog over the Model Context Protocol on stdio, with the Robot tools included by default (`--no-robot` to omit them). Point Claude Desktop or Claude Code at it and an LLM can read every component's props schema and drive a running app: fill out forms, navigate, assert state, call exposed component methods.
// claude_desktop_config.json — the CLI itself is the server:
{
  "mcpServers": {
    "idealyst": { "command": "idealyst", "args": ["mcp"] }
  }
}
The catalog behind it covers every `#[component]`, props struct, primitive, guide, and theme token in the project and its component-library dependencies — `idealyst catalog-json` prints the same data for editor tooling. Recipes keep it honest: a recipe is a compiled usage example, so a props change that breaks one fails the build before the docs or the LLM context can drift.The rest of the tooling → CLI
Gated on a Cargo featureThe Robot bridge + registry compile in only when the `robot` feature is on. Production release builds leave it off; there's no runtime overhead and no exposed surface in shipped binaries. Dev builds auto-enable it via the `runtime-core/dev` feature.
