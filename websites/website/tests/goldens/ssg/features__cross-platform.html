Cross-platform
Cross-platformThe same Rust code renders natively on phones, desktops, the browser, a GPU surface, and the terminal. Each platform is one implementation of the same backend traits.
One component treeComponents are written against a fixed set of primitives (view, text, button, scroll_view, and the rest) plus signals for state. The CLI builds and wraps the same code for each target.Per-platform differences in layout, events, and rendering are handled below the primitive layer, not in application code.
#[component]
fn app() -> Element {
    let count = signal(0);
    ui! {
        view {
            text { format!("Taps: {}", count.get()) }
            button(
                label = "Tap".to_string(),
                on_click = move || count.update(|n| *n += 1),
            )
        }
    }
}

// Ship the SAME function to every target:
//   idealyst run ios        → UIKit
//   idealyst run android    → Android Views
//   idealyst dev --web      → WASM + DOM
//   idealyst run macos      → AppKit
Native widgetsA button is a UIButton on iOS, an Android button view over JNI, an NSButton on macOS, and a <button> in the DOM. A scroll_view is a UIScrollView, an Android scroll container, an NSScrollView.Scroll physics, text selection, the system back gesture, accessibility focus, and keyboard handling are the platform's own implementations.Targets without a native toolkit (a bare GPU surface, a terminal grid) render the primitives through their own drawing layer instead.
Consistent behaviorBackends differ in mechanism and converge on the same result. A scale animation uses UIView.transform on iOS, a CALayer transform on macOS, and CSS transform on web.When a primitive renders differently on one backend, the fix goes into that backend. There are no per-platform adjustments in application code or in the framework's call sites.
The platform seamHost covers the structural operations — how nodes are parented, reordered and removed. Primitives (create / update), style application, layout, refs, and animated values arrive as separate capability traits. Routing, theming, components, and reactivity sit above them and are backend-independent.Adding a target (a proprietary display, a server-side renderer, a games console) means implementing that seam and the capabilities the target supports.Platform-specific capabilities like maps, video, and web views register as third-party extensions on the scene registry instead of growing the seam. The Extensibility page covers that mechanism.
// The structural seam — seven operations.
impl Host for MyBackend {
    type Node = NodeId;
    fn insert(&mut self, parent: &mut NodeId, child: NodeId) { ... }
    fn remove_child(&mut self, parent: &NodeId, child: &NodeId) { ... }
    // ...clear_children, insert_at, create_anchor, supports_splice
}

// Primitives, style, events — one capability trait each.
impl caps::TextOps for MyBackend { ... }
